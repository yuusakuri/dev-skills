# なぜこの順序なのか

どのスキルを使うかは`development-lifecycle`ルーター、または[カタログ](../reference/catalog.md)が答えます。

このページが答えるのは別の問いです。なぜ工程がこの順に並んでいるのか。

原則は、決定は早く書き留めるほど変更が安く済む、ということです。各工程は、ある種類の誤りをまだ安く直せる時点に置いてあります。

## 各工程が確定させるもの

| 工程 | 確定させるもの | 飛ばした場合の損失 |
| --- | --- | --- |
| 把握 | このプロジェクトがどう動いていて、変更をどこに置くか | 既存の慣習と衝突する変更になる。既にあるコードを重複して書く |
| 要件 | 「完了」の意味を、書かれた形で | 争いがレビュー時に持ち込まれ、書かれたものがないので決着しない |
| アーキテクチャと設計 | 構造、インターフェース、データモデル、認証・機密情報・個人情報・金銭・信頼できない入力に関わる箇所 | 次の担当者が、意図したトレードオフと事故とを区別できず、覆してしまう |
| 計画 | 作業の順序と、何をどの層でテストするか | テストの層が実装中の圧力下で決まり、最も速く書けるテストが選ばれる |
| 実装 | コード | — |
| デバッグと性能 | 何が悪いのかを、変更する前に計測して | 見当違いの原因に手を入れる |
| 検証 | コマンドを実行し、出力を読んだこと | 動かないものにレビュー1周、あるいはリリース1回を費やす |
| レビュー | その変更が何を露出させるか、追加した依存が何を持ち込むか | — |
| リリース | 計測、次に判断、次に本番での確認 | 計測は障害の最中には足せない。失敗前に出力していたものが、得られる情報のすべてになる |
| 運用 | まず復旧、理解はその後 | 利用者が影響を受けている最中の原因究明は、5分の問題を1時間に変える |

2点は明示しておく価値があります。

決定記録は、最も速く失われる部分である論拠を先へ運ぶ手段です。設計の工程に属しますが、読まれるのは数か月後のレビューです。

振り返りは、障害の代償を何かに換える手段です。全員が疲れているときに省くと同じ障害が二度起き、最初の振り返りの対策が一度も実行されていなかったことが、そこで分かります。

## この順序が当てはまらない場合

検査の失敗は実装へ戻ります。先へは進みません。

レビュアーの「なぜこう作ったのか」は、たいてい決定記録が無いという意味です。

振り返りで挙がった対策は要件なので、機能と同じ場所で管理します。

「何が起きているのか分からなかった」は振り返りで最も多く挙がる指摘で、その対策は次の変更と一緒に出ます。
